What this is

Case C — the same minor issue, twice in a row → forced ROLLBACK

Not every bad deployment looks dramatically broken. Sometimes a canary is almost fine — one metric just over its limit, everything else healthy — and on its own, that single deployment would reasonably PROMOTE. The problem is when that exact same metric keeps doing it, release after release. The gate catches that pattern specifically.

✓ PROMOTE
1st deployment — one minor breach, otherwise healthy
Health score70.0 / 100
Breachredis_latency = 11ms (limit 10ms)
Persistent breachesnone yet
✗ ROLLBACK
2nd deployment — same issue recurs
Health score70.0 / 100 (unchanged)
Breachredis_latency = 11ms, again
Forced override
  • redis_latency breached its SLA in 2 of the last 2 deployments
forced_rollback: true

Same health score both times — 70.0. The only difference is that this is the second time this metric has broken its SLA for this service. The gate treats that pattern as proof of a real, standing problem and overrides the score, rather than letting the same issue quietly repeat indefinitely.

Why this matters — the business case

Without an automated gateWith the Raptor Gate
A human watches dashboards after every deploy and decides whether it's safe The decision is automatic, consistent, and takes seconds
Judgment calls vary by who's on call and how tired they are Every deployment is scored against the exact same rules and model, every time
Subtle cross-metric issues are easy to miss individually The Isolation Forest is trained specifically to catch combinations no single threshold would flag
Bad deployments can sit in production for minutes or hours before anyone notices Rollback happens automatically, immediately, as part of the deployment pipeline itself
Rollout decisions aren't repeatable or auditable Every decision ships with full supporting evidence for audit and post-incident review
A minor, recurring issue can keep slipping through if each individual deployment looks "good enough" on its own The gate remembers recent deployments per service and forces a rollback the moment the same metric breaks its SLA repeatedly — a pattern no single snapshot would catch

Built-in safety model

Fails closed, never open

If the gate cannot reliably collect metrics, it does not guess — it automatically returns ROLLBACK. Uncertainty itself is treated as a reason not to promote.

A recurring issue overrides a passing score

If the same metric breaks its SLA across multiple recent deployments, the gate forces a rollback outright — see Case C above. One acceptable-looking deployment is never allowed to mask a pattern of the same problem repeating.

Notification failures never change the decision

Optional integrations with GitLab, Jenkins, or a webhook are additive. If a notification fails to send, the deployment decision itself is completely unaffected.

Secrets are never stored in config

Credentials are read from the environment only — nothing sensitive is ever committed or hard-coded.

Design principle: the gate would rather block a good deployment on a false alarm than ever let a bad one through on missing data.

Fits into existing CI/CD — no rip-and-replace

The gate is a single command with a single, simple contract: exit code 0 to promote, exit code 1 to roll back. Any pipeline — GitLab CI, Jenkins, or a custom script — can branch on that exit code directly, with no proprietary platform required and no changes to how deployments are already triggered. It can also actively notify a pipeline via webhook, GitLab trigger, or Jenkins job parameters the moment a decision is made.
